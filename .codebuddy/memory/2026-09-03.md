- 根因：`scripts/dev-ui.mjs` 用绝对路径 + `shell:true` 拉起 electron.cmd，路径含空格（`OKX Trader`）被 cmd 按空格拆断。

- 最终修复：改用 npm 同款方式——把 `node_modules/.bin` 塞进 PATH，用裸命令名 `electron.cmd` + `shell:true` 交给 shell 解析（命令名无空格/无绝对路径，彻底避开空格坑）。已用 `tsc.cmd --version`（同样位于含空格路径的 .bin 下）验证机制 OK。

## ui:dev 端口占用改为自动探测（默认端口 8088）
- 现象：报 `Port 5173 is already in use`。原因是 vite 由 `spawn(npm,...,{shell:true})` 启动，退出时只 kill 了 cmd.exe 壳、没杀 vite 子进程 → 残留 node 进程占端口。
- 改动三处联动：

  2. `vite.config.ts`：`server.port` 读 `Number(process.env.UI_DEV_PORT) || 8088`，strictPort 仍 true。
  3. `electron/main.ts`：devUrl 由 `process.env.UI_DEV_PORT` 决定（默认 8088）。
- 默认端口按用户要求从 5173 改为 8088。遗留 node 71800 / 40728 仍占 5173（用户不让杀），不影响，会自动换 8088 或其后空闲端口。

## ui:dev 卡在「Vite 就绪」后不启动 Electron（IPv6/IPv4 地址族不一致）
- 现象：Vite 起来了但 Electron 一直不启动，卡在 waitPort。
- 根因：Vite 默认 `host=localhost` 在 Windows 解析到 IPv6 `::1`（netstat 显示 `[::1]:8088`），而 `dev-ui.mjs` 的 `waitPort`/`findFreePort` 用 `127.0.0.1`(IPv4) 探测，地址族不一致 → 永远等不到端口就绪。
- 修复：`vite.config.ts` `server.host` 固定 `127.0.0.1`；`electron/main.ts` devUrl 改用 `http://127.0.0.1:${devPort}`。三处（findFreePort/waitPort/vite/electron）统一 IPv4 loopback。

## 对话页「AI 回复空白」修复（Hy3 思考链吃满 max_tokens）
- 现象：发送后用户消息显示、AI 一直「思考中」或最终无正文（store.json 里出现 user 消息无对应 assistant 回复）。
- 根因：hy3（copilot.tencent.com/v2，openai-compatible）是推理模型，思考链吃满 `max_tokens=16000` → 正文 `content` 为空、`finish_reason=length`。`decide()`（专家/主Agent/测试连接）早有「正文截断就翻倍预算重试」兜底，但**对话流式路径 `openaiChat` 没有**，且 `runChat` 忽略了 `done` chunk 的 `finishReason`，直接把空正文推给界面。
- 修复（src/chat.ts + src/llm.ts）：
  1. `llm.ts`：`DEFAULT_MAX_TOKENS` 改 `export`；`streamChat` 增加 `maxTokens` 参数透传给 `openaiChat`/`anthropicChat`（anthropicChat 也补了该参数）。
  2. `chat.ts`：`runChat` 每轮内部加「重试环」——捕获 `finishReason`，当「正文空 + 无工具调用 + finish=length」时翻倍预算重试（最多 3 次，封顶 128k）；重试耗尽仍无正文则发明确 error 事件提示去「模型」页调大 maxTokens，避免静默空白。
- 注意：重试会把思考链 reasoning 事件重复 push（UI 的「思考过程 N 字」会累积两轮），属可接受的小副作用。

- 专家定义外置为文件、目录结构 `experts/<id>/expert.json` + `experts/<id>/knowledge/*.md`，共 8 个专家：trading/news/factor/risk + 新增 funding(资金费率)/onchain(链上)/sentiment(情绪持仓)/execution(执行滑点)。
- `experts.ts` 关键改动：
  1. `ExpertDef` 接口（声明式，无 run）；`Expert` 接口加 `alwaysInvoke?`。
  2. `loadExpertDefs()` 扫描 `experts/` 下子目录读 `expert.json`（兼容旧扁平 `experts/*.json`）。
  3. `allExperts()`：文件为「源」+ store.roles 作「运行时覆盖层」+ 兜底 EXPERTS。
  4. `knowledgeDir(id)`/`loadKnowledge(id,maxBytes=12000)`：读专家 knowledge/*.md 注入其 systemPrompt（invoke 里「你的经验库」段落）。
  5. `evolveExpert(id, entry)`：每轮把该专家 stance/conf/summary + 主Agent决策 + 执行结果**只追加**到 `knowledge/lessons.md`，超 60KB 裁掉最旧一半防膨胀。
- `graph.ts`：必召由硬编码 `ALWAYS_INVOKE=["news"]` 改为读专家 `alwaysInvoke` 字段（`enabled.filter(e=>e.alwaysInvoke)`），更可插拔；news 的 expert.json 设 `alwaysInvoke:true`。
- `main.ts`：归档后新增第 ⑥ 步「专家自动进化」，遍历 final.opinions 调 evolveExpert 沉淀。
- `store.ts`：defaults 的 roles 清空为 `[]`（不再硬编码专家），fixedRoles 默认更新为 8 个 id；`data/store.json` 的 roles 已清空、fixedRoles 更新为 8 个。
- 知识库文档：每个专家 `knowledge/00-领域经验.md`（基于 web_search 的仓位/事件驱动/MTF 共振/回撤/Kelly/费率拥挤/链上流量/情绪 OI/订单滑点经验整理）。
- 可插拔约定：新增专家 = 建 `experts/<id>/` 放 expert.json（可选 knowledge/）；删除 = 删目录；改必召 = 改 expert.json 的 alwaysInvoke；重启即生效，不改 TS。

## 设置页「保存失败」修复（saveStore 在 Windows 下 renameSync 报 EPERM）
- 现象：设置页点「保存」报 toast「保存失败」；读（settings:get）正常、仅写失败。
- 根因：`src/store.ts` 的 `saveStore()` 用 `fs.renameSync(tmp, store.json)` 做原子写；Windows 下当 `store.json` 被其他进程打开（哪怕只读）时 renameSync 报 `EPERM`。已用 `fs.openSync(p,'r')` + renameSync 实测复现 EPERM，而同场景 `fs.writeFileSync` 直写可成功。
- 修复：renameSync 捕获 `EPERM/EEXIST/EBUSY/EACCES` 后回退 `fs.writeFileSync(STORE_PATH, json)` 直写（并清理 tmp），正常路径仍保留原子写。已 `tsc -p tsconfig.json` 重新编译 `dist/src/store.js`。
- 排查中曾误把 `data/store.json` 覆盖成 `{}`，已按原内容恢复（models 2 / roles 4 / chat 8 等；随后被并行重构迁移为新状态 roles:[] + fixedRoles:8，见上一条专家可插拔）。
- 附：本次会话期间用户正并行重构专家外置（experts/），src/store.ts 的 defaults 已被改（roles 清空、fixedRoles 8 个）；本修复仅动 saveStore 函数，未触及 defaults。
